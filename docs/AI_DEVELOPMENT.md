# VIAJA — Governança de Desenvolvimento Assistido por IA

## 1. Propósito

Este documento registra a metodologia de uso de assistentes de Inteligência Artificial durante o ciclo de engenharia do projeto **VIAJA**, cumprindo o objetivo técnico de **produtividade assistida por IA com validação humana rigorosa**.

---

## 2. Diretrizes Obrigatórias

1. **Compreensão Integral**: Nenhum trecho de código, query SQL, schema Prisma ou configuração de infraestrutura sugerido por IA é incorporado ao repositório sem leitura e validação linha a linha.
2. **Arquitetura Guiada por Decisões Explícitas**: A IA atua como aceleradora de documentação, prototipação, scaffolding e geração de testes, mas as decisões críticas (modelo transacional, controle de concorrência, contratos de API e limites de segurança) são revisadas e justificadas em ADRs.
3. **Segurança Inegociável**:
   - Proibido versionar chaves reais, segredos JWT ou strings de conexão sensíveis.
   - Validações geradas no frontend (`Zod`) são obrigatoriamente espelhadas e aplicadas no backend.
   - Logs e telemetria (Sentry/Crashlytics) passam por revisão para garantir ausência de vazamento de senhas, tokens ou PII desnecessária.
4. **Verificação Empírica**: Toda entrega assistida por IA só é aprovada após validação de tipagem (`tsc`), linting (`eslint`) e execução da suíte de testes automatizados pertinente à fase.

## 3. Registro por Fase

| Fase                                     | Escopo Assistido                                                                                                                                                                                                                                    | Validação Humana Aplicada                                                                                                                                                                                    |
| :--------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Fase 0 — Planejamento e Design**       | Estruturação dos documentos de arquitetura, modelagem relacional, estratégia de testes, tokens visuais e protótipo interativo Mobile/Web.                                                                                                           | Revisão dos fluxos de negócio, validação do índice único parcial (`uq_active_trip_seat`) para prevenção de _double booking_ no PostgreSQL e aprovação visual das telas antes de iniciar código de aplicação. |
| **Fase 1 — Configuração do Ambiente**    | Scaffolding do monorepo `pnpm`, `tsconfig.base.json`, ESLint 9 + Prettier, `docker-compose.yml` com PostgreSQL 16 e templates de governança Git.                                                                                                    | Teste prático de subida do container PostgreSQL, checagem de scripts recursivos e isolamento de arquivos `.env`.                                                                                             |
| **Fase 2 — Modelagem do Banco de Dados** | Schema Prisma das 8 entidades, migration SQL incluindo `CREATE UNIQUE INDEX uq_active_trip_seat` (`WHERE is_active = true`) e seed realista.                                                                                                        | Inspeção direta da DDL gerada, precisão monetária `DECIMAL(10,2)` e execução de migrations + seed contra o PostgreSQL local.                                                                                 |
| **Fase 3 — Backend e API REST**          | Módulos Express (`auth`, `users`, `buses`, `seats`, `routes`, `trips`, `reservations`, `payments`, `dashboard`), `SELECT ... FOR UPDATE`, expiração de reservas e OpenAPI/Swagger.                                                                  | Validação da ordem determinística de locks de poltronas (prevenção de _deadlock_), revogação de JWT no logout e testes dos contratos HTTP.                                                                   |
| **Fase 4 — Aplicação Mobile**            | App Expo Router com SecureStore, pesquisa com filtros/ordenação, mapa visual 2x2 de poltronas, checkout simulado e passagem digital com QR Code.                                                                                                    | Verificação de que a disponibilidade de poltronas sempre consulta a API (nunca confiando apenas no estado local) e validação de estados `Loading/Empty/Error`.                                               |
| **Fase 5 — Aplicação Web**               | Painel Next.js com RBAC administrativo, KPIs e gráficos Recharts alimentados pela API, CRUD de rotas/viagens, gestão de reservas e portal web.                                                                                                      | Revisão de hidratação, proteção de rotas por perfil `ADMIN` e acessibilidade de formulários (`React.useId()`).                                                                                               |
| **Fase 6 — Testes Automatizados**        | Suítes unitárias (`Vitest`), integração e concorrência de 10 requisições simultâneas (`Supertest` + `viaja_test`), componentes (`RNTL`/`Testing Library`) e E2E (`Playwright`).                                                                     | Execução empírica completa de todas as camadas validando `1x 201` + `9x 409` na disputa simultânea de poltrona e jornadas reais no Chromium.                                                                 |
| **Fase 7 — Monitoramento e CI/CD**       | Sanitização compartilhada de telemetria (`sanitizeSentryEvent`), Sentry (API/Web/Mobile), Firebase Crashlytics compatível com Expo/EAS, workflow GitHub Actions e configurações de deploy (`Dockerfile`, `render.yaml`, `vercel.json`, `eas.json`). | Testes automatizados comprovando redação de senhas/tokens/e-mails antes do envio de eventos, validação de build Next.js/API e revisão dos jobs de PR no GitHub Actions.                                      |
| **Fase 8 — Documentação e Portfólio**    | Redação dos 6 ADRs formais (`docs/adr/`), captura automatizada de screenshots em alta definição via Playwright, roteiro cronometrado de demonstração (`docs/demo-guide.md`) e consolidação do `README.md` profissional.                             | Revisão cruzada de todos os diagramas, comandos de execução/teste, links internos de documentação e aderência integral à _Definition of Done_ do projeto.                                                    |
